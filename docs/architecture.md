# ORBIT architecture and feature definition

The logging interface records more detailed data than the current analysis vector represents. This distinction is central to evaluating the prototype.

## Configurable check-ins

Schema version 22 keeps two different kinds of check-in data, plus the older detailed logs.

`CheckInRecord` and `CheckInAxisValue` are state observations. `CheckInAxis` defines a named 0–10 scale. Stable default axes are mood, energy, confidence, and anxiety. The check-in screen saves explicit values with trigger `manual`. An untouched slider is not saved. A selected emotion is stored on `CheckInRecord` whether or not the numeric mood axis was set. An empty emotion stays empty. The emotion is a name snapshot, not a foreign key to the emotion list. A `MoodSample` with source `check_in` is inserted in that same transaction only when the mood axis is explicit, because a mood sample requires a score. That sample receives the check-in's emotion string. Selecting only an emotion does not invent a mood score or a mood sample. Records migrated from schema 21 receive an empty emotion; they are not matched back to an older mood sample by time. The committed mood, which lives in preferences rather than Room, is updated only after that transaction succeeds. If that cache write fails, the check-in is still saved and the app still leaves the context screen. The failure is logged rather than shown as a failed check-in. The next launch copies the latest `MoodSample` back into the cache when that sample is at least as new as the stored commit. An untouched mood axis inserts no mood sample and does not change the committed mood. Other axes are not copied into `MoodSample`.

Next on the mood log opens the context overview without writing. Save on that overview writes the check-in, the activity, workout, usage, and diet reports, the legacy mood sample, and `completedAt` together. Cancel on the mood log or the context overview leaves the whole check-in, writes nothing, and clears the sliders, note, emotion, and logged time. Back from a category returns to the overview without writing.

`CheckInContextWindow` is the interval the person was asked about, ending at that check-in's `recordedAt`. Its start is snapshotted once: the previous same-day check-in, otherwise that day's logged wake time when the wake is not after the check-in, otherwise the local start of the day. A later backdated check-in does not rewrite a window already stored. A long-press on that history row can replace the stored start or the stored end. The end stays equal to `recordedAt` and to the legacy mood sample's time. The start basis, the previous check-in, and every other entry stay as they were. `previousCheckInId` is cleared if that earlier check-in is deleted, and the stored start time stays. Each window has four `CheckInContextCategory` rows — activity, workout, diet, and usage — created as `none`. `CheckInActivityItem` records activities attributed to that interval, with the displayed name kept as a snapshot and `reportedAt` marking when the report was saved. `CheckInWorkoutItem` does the same for workouts and also stores an approximate duration in minutes. One row is one workout, so the same type can appear more than once. `CheckInUsageItem` records supportive or coping use in that interval. `intent` is `SUPPORTIVE` or `COPING`. `name` is a snapshot, `substanceOptionId` is a nullable reference with no foreign key, and `amount` is optional text for the whole interval, such as "10 mg" or "2 drinks." The same option is stored once; repeated use is summarized in the amount. `CheckInMeal` is one eating occasion in the interval. `size` is one of `snack`, `small`, `medium`, or `large`, a subjective description for that person, not a calorie or universal portion. `sortOrder` is the order they entered, not a clock time. `CheckInMealFoodItem` optionally names foods in that meal. `foodName` is a snapshot, `foodOptionId` is a nullable reference with no foreign key, and the same option may appear in another meal but not twice in one meal. A meal with no food items is still a valid observation. These items do not invent an occurrence time. Saving an empty activity, workout, usage, or meal selection stores status `none` and no placeholder item.

The context overview is where activity, workout, usage, and diet are edited before anything is stored. Each category starts as `none`. Opening one adjusts its list, and Save stores that list as it stands: an empty list stays `none`, and one or more items becomes `entries`. Those choices stay in memory until the overview Save. A selected usage option starts from its `defaultAmount`, and that amount is stored only when the overview is saved. Contextual foods are not analysis axes. `completedAt` is set by that same Save. It marks that the overview was saved, not that every category had items. Save returns to the check-in screen and removes the context screens from the back stack.

Detailed `ActivityEvent`, `WorkoutEvent`, meal, sleep, and usage logs remain a separate logging path. A contextual workout is an approximate report inside the check-in interval. A `WorkoutEvent` is an exact log with start, end, mood, and the other session fields. A contextual usage item says something was used during the interval. A `SubstanceUseEvent` claims a particular time and keeps its older event fields. A contextual meal is an approximate report of an eating occasion inside the check-in interval. A `MealEvent` is a separate log with an exact timestamp, weights, and optional nutrient data. Replacing contextual items does not modify `ActivityEvent`, `WorkoutEvent`, `SubstanceUseEvent`, or `MealEvent` history, and older events are not copied into the contextual tables. The detailed activity, workout, use, and diet screens still have their own event fields. The detailed diet screen still has barcode lookup, food search, and nutrient calculations.

The fixed ten-axis state vector is obsolete. `FeatureAxes`, `StateEncoder`, `StateVectorSnapshot`, `TopologyRepository`, `HnswIndex`, and `TopologyHarness` remain in the source tree, and their Room tables remain in schema 23, but the application does not construct them, warm them, schedule them, or show a control that writes them. They are not a compatibility target for check-ins or wearable observations.

## Check-in analysis representation

`domain/checkin/CheckInAnalysisDatasetBuilder` is a pure projection of the schema 22 check-in entities. It does not read or write Room, and it does not feed `FeatureAxes`, `StateEncoder`, `StateVectorSnapshot`, or topology. The dataset protocol is `check-in-analysis-v2`. Its source schema is Room version 22. Nothing in this layer is clustered, smoothed, imputed, or turned into a recommendation.

`StateObservationV2` is one check-in. Each explicit `CheckInAxisValue` keeps its raw integer and a convenience `raw / 10.0`. That division does not mean adjacent scores are equally far apart. A missing axis stays missing: it is not stored as 0, 5, or 0.5. A recorded 0 stays present and distinct from missing. Anxiety is not inverted, so a higher raw value means more anxiety. Axes other than the four defaults remain in the general axis map. The core view is only `mood`, `energy`, `confidence`, and `anxiety`, in that order. `trigger`, `note`, and `emotion` are copied from `CheckInRecord` as raw strings. They are not axes, the note is not embedded, and an emotion is not given a number. An empty note or emotion stays empty. Emotion in this projection comes from the check-in row, not from a mood-sample match. The latest check-in line and composite history cards do the same, and use the legacy mood-sample emotion only when the check-in emotion is empty. Older mood rows that are not check-ins still come from `MoodSample`. `hasObservedAxes`, `observedAxisCount`, and `coreAxisCount` describe how much of the state was recorded. A check-in with no axis values stays in the dataset.

`ContextIntervalObservationV2` is the stored context window that ends at that check-in. Duration is `windowEndAt - windowStartAt`. Activity, workout, diet, and usage stay structured: option id and name snapshot, workout duration, meal size and foods, and usage intent plus the original amount text. Amount text is not parsed. `none` is an observed empty category, not missing data. A missing category row stays `absent` and is reported as an issue. `unreviewed` stays `unreviewed` and is not rewritten to `none`. An incomplete interval may still be `unreviewed`. A completed interval with an `unreviewed` category is a protocol inconsistency and is reported. `completedAt` set means the overview was saved. `completedIntervals()` is that subset. The dataset's `intervals` list still contains incomplete windows. Completion is not a judgment that the rows are consistent.

`StateTransitionObservationV2` is created only when `previousCheckInId` names a check-in in the same input. That is a linked transition, even when the delta map is empty. A measured delta exists only for an axis recorded at both endpoints: ending raw minus previous raw. `hasMeasuredDelta` is false when no axis overlaps. Wake-time and day-start windows remain intervals. They have no previous check-in, so they have no transition and no invented starting state. The summary counts linked transitions and measured-delta transitions separately.

The recorded relationship is `State_t --[context during the interval]--> State_t+1`. A state holds the psychological observation at its timestamp: emotion, the explicit axis readings, which core axes are present or missing, and the trigger and note. Emotion stays a name. Activity, workout, diet, and usage belong to the interval that ends at a check-in, not inside either state. `directedSteps()` names that existing transition as a starting state, that interval, and the ending state. It does not copy the rows into a second dataset. The interval saved with the ending check-in is the context that led from the previous state to that ending state. When a later check-in arrives, its window is the outgoing interval of the current state (`outgoingInterval`). That later window is not folded back into the current state, and the next observation's axes and emotion are not readable from it. A wake-time or day-start interval stays a context observation with no measured starting state. `outgoingInterval` returns the first matching window. A later check-in can leave an earlier window pointing at the same previous check-in, so one state can have more than one outgoing interval.

`projectAlternatingTemporalGraph` is a pure view of that same dataset. It does not read or write Room, and it does not assign clusters, coordinates, or weights. A state node is one `StateObservationV2`, keyed by the check-in id. Identical axis values and the same emotion stay separate nodes. A transition node is one `ContextIntervalObservationV2`, keyed by `endingCheckInId`. That string is also the ending state's id; the two nodes stay different objects. The transition points at the existing interval and, when the previous id resolves, at the existing `StateTransitionObservationV2`. It does not copy axis maps, category rows, or deltas. Wearable observations are not on the analysis interval, so this graph does not attach them. Incoming and outgoing transition ids are lists, ordered by the ending check-in's recorded time and then by id. That order does not change an id or which endpoint was stored as the start.

A wake-time or day-start interval is a transition with an ending state and no start state. An unresolved `previousCheckInId` keeps the interval and the existing missing-previous issue, and it does not add a state. A previous check-in that is not earlier stays linked in the stored direction and keeps that issue. Neither case is rewritten. `RetrospectiveNeighborhood` names one state's incoming and outgoing transition ids and the neighboring state ids those transitions resolve. It looks in both directions and does not walk further hops.

`CausalTransitionInput` has the transition id, the starting state when one resolves, and the interval. It has no ending state, no delta, and no neighborhood. `CausalPredictionTarget` holds the ending state on a separate object. Every interval gets a causal step, including the ineligible ones. A step is ineligible when the start does not resolve, the interval is a wake or day-start boundary, the stored previous check-in is not earlier, `completedAt` is null, or the interval disagrees with itself: the window end differs from the check-in, a category status disagrees with its items, a completed interval still has an unreviewed category, or a category kind is conflicting. A missing category row stays absent and does not by itself remove eligibility. An empty delta map does not remove the link. No message-passing update runs in this pass. `directedSteps()` is not this input, because that view includes the ending state.

`projectContextualEvidence` is a pure view of that graph plus the wearable stream. It does not write Room, and it does not build feature vectors, weights, or coordinates. `StateOccurrenceKey` and `TransitionOccurrenceKey` wrap the graph's existing strings. The same raw check-in id is both a state and the transition that ends there; the two key types are not interchangeable, and the graph ids themselves are unchanged. A frame pairs a key with a payload and with metadata. The payload has no occurrence id. State evidence copies explicit axis readings, including custom axes, the existing `raw / 10.0`, core axes that are missing, and conflicting axes as a separate list. A recorded 0 stays present. An empty emotion stays absent. The emotion is a name. Anxiety is not inverted. The note, trigger, local date, and recorded time are metadata, and the note is not embedded. Transition evidence copies the interval's instants, duration, start basis, and completion, then activity, workout, diet, and usage in their existing order and category kind. `none`, `entries`, `unreviewed`, `absent`, and `conflicting` stay distinct. Option ids and meal-size labels stay categorical. Usage amount text stays unparsed. A workout duration of 0 cannot occur: the entity requires 1 to 1,440 minutes, so a missing workout is a category kind. Meal `sortOrder` is entry order, not a size rank.

Wearable rows are joined with `IntervalWearableSelection`, the same selection History uses. An exact aggregate replaces other contained spans of that metric. A wider cumulative window stays overlapping and is left off. Several contained spans with no exact aggregate are kept and are not summed; `competingSpans` marks that case. Resting heart rate keeps the latest point. No selected row is `Unobserved`, not a numeric zero. A stored zero stays on the referenced `WearableObservation`. Sleep is not selected. Those references are not copied onto state evidence. The projection builds its state, transition, and wearable maps once.

A retrospective state view names incoming and outgoing transition keys. A retrospective transition view names the resolved start key, when there is one, and the ending state key. A causal example is one graph `CausalStep`. Its input has the starting payload, or null when the graph has no start, and the transition payload. Its target has the ending payload. The example key sits on the example, outside that input. The input does not carry the ending key, the ending payload, a delta, the linked transition, or a neighborhood. Eligibility and its reasons are the graph's.

`encodeFeatures` fits named base vectors on that evidence. It does not pass messages, scale blocks, or assign latent coordinates, and it does not store the vectors. Each feature has a typed semantic key, a diagnostic name, a block, and an index. Encoding reads the key. The name is not parsed back into a meaning. A token character outside letters, digits, `_`, and `-` is written as `%`, the hexadecimal code point, and `;`. `%` itself is escaped that way, so two different tokens cannot share a diagnostic name, and a unit such as `fl.oz` is not split on the dot. A vector stores a number and a separate observed mask. An unobserved slot is `0.0` with the mask false. A recorded zero is `0.0` with the mask true. Core axes are always in the state schema. A custom axis is included only when some state records it or lists it as conflicting. Emotion is a presence bit per label that appears, plus an observed indicator. An empty emotion leaves those bits unobserved. Anxiety is copied from the evidence normalization and is not inverted. Notes, triggers, local dates, recorded times, interval endpoints, report times, meal order, and occurrence ids are not features.

`UsageAmountParser` reads one amount phrase and leaves the stored text unchanged. A blank phrase is missing. One nonnegative decimal, optionally followed by one unit token, is parsed. `μg` and `µg` become `mcg`. A short alias list folds capitalization and a few singular and plural forms. Unknown units stay their own group, and `mg` is not converted to `g`. Trailing prose, negatives, and nonfinite text stay unparsed. Presence is recorded for an identity and an intent before any unit split. The identity is the option id, or the case-folded name when there is no option id. A blank or unparsed amount still marks that identity present. `present`, `entries`, and the parsed, missing, and unparsed counts stay observed when the category is `none` or `entries`. `amount_complete` is 1 only when every matching entry parsed, including when no matching entry occurred. Numerical totals are observed only in that complete case: amounts sum inside one normalized unit, a fitted unit that did not occur is an observed zero, and a literal parsed 0 stays an observed zero. If any matching entry is missing or unparsed, every unit total and the per-hour rate for that identity and intent stay unobserved. The encoder does not substitute zero and does not keep the sum of the parsed subset. A per-hour rate exists only for the unitless group, and only when that group is complete and the duration is positive. A physical unit has no rate. All of those usage features stay unobserved when the category is absent, unreviewed, or conflicting. The category kind itself is a separate protocol block.

Wearable features use the selected references. One steps span, one resting point, and one heart-rate average contribute their value when the unit matches. Heart-rate samples contribute a count, mean, minimum, and maximum. `competingSpans`, more than one span, or a mismatched unit leaves the aggregate unobserved and marks the metric ambiguous. Sleep is not a feature. The schema is fitted on the evidence it is given. That describes this dataset. A later held-out evaluation has to fit on training evidence only.

`projectLocalContext` prepares those base vectors and adds one bounded round of local context. It does not aggregate days or weeks, reduce dimensions, cluster, train, predict, or write Room. `fitFeaturePreparation` reads the encoded states and transitions it is given and can be passed back in, so a later evaluation can fit on training vectors and transform held-out vectors with the same statistics. Fitting the supplied dataset is not that evaluation. Substantive numeric features use the observed mean and the root-mean-square deviation from that mean. Unobserved mechanical zeros are left out of the fit. A numeric feature with no usable observations, or a root-mean-square deviation no larger than `1e-8` times its magnitude, becomes a transformed zero, keeps its observed mask, and is marked nonvarying. The magnitude is at least 1. Ordinary differences are not clipped. A binary column is nonvarying when every observed value is the same bit; a missing row is not counted as a different value. Each substantive block keeps every column and records both the total count and the effective varying count. Its factor is the equal block weight over the square root of the effective count. A block with no varying column uses factor `0` and adds no pairwise distance. The factor is a property of the fitted schema. Protocol, masks, ambiguity, amount completeness, and parse counts stay in a quality channel and do not move the geometry. An unobserved amount or wearable value keeps a false mask there. A retrospective transition holds the balanced transition, the resolved start state, and the end state as separate segments. A missing start is unavailable rather than a psychological zero. A message carries the balanced base transition and the opposite endpoint's base state, not the focal state and not the retrospective or contextual vector. Messages in one direction are pooled by a mask-aware mean, with incoming and outgoing kept apart. A contextual state holds its base geometry, that incoming pool, and that outgoing pool. The causal prepared input holds the balanced starting base state, when one exists, and the balanced transition. Its target is the balanced ending base state and is not read while the input is built.

`projectMultiscale` adds fixed trailing context on top of that local state. It does not build adaptive regimes, reduce dimensions, or feed the result back into transitions. For an anchor at time `t`, the trailing day is `[t - 24 hours, t)` and the trailing week is `[t - 7 days, t)`, both elapsed durations. States and intervals are placed with the same half-open rule as `TemporalWindowProjector`: a state at `t - 24 hours` is inside, the anchor state is outside, and an interval is included only when `classifyInterval` says it is fully contained. An interval whose exclusive end is `t` is contained. One that crosses the start stays whole and is overlapping, so it is counted and left out of the aggregates. An incomplete contained interval is counted and left out as well. State summaries report a mask-aware mean, population deviation, minimum, maximum, and, for an axis with two distinct timestamps, a least-squares slope per hour. Emotion presence can contribute its mean and does not get a slope. Transition means are mask-aware; for a presence bit the interval prevalence is the fraction of observed intervals with that bit, which is not minutes and not a causal effect. Current-minus-day, current-minus-week, and day-minus-week are plain differences of those balanced state coordinates, and either side missing leaves the difference unavailable. The retrospective multiscale state keeps local incoming and outgoing context. Its day and week descriptors are still trailing-only. A causal input takes the descriptor anchored at the starting state, the separate prepared transition, and a separate base target. It does not take outgoing local context, a descriptor anchored at the target, or an interval that ends after the start. Twelve major segments share equal schema-level weight. Each segment's factor is that weight over the square root of the effective blocks it represents. A row with an unavailable segment does not rescale the others. `flatten` applies those factors in a fixed segment order. Fitting the dataset in hand is still not a held-out evaluation.

`fitRetrospectiveLatentProjection` fits a descriptive PCA on that retrospective flat vector. The protocol is `retrospective-multiscale-pca-v1`. It is dataset-relative, not causal, not diagnostic, and not stable across refits, and those limits are fields on the model. The coordinates are not written onto `CausalMultiscaleInput`. Column metadata follows `flatten` and keeps the segment, semantic, diagnostic name, block, and both factors. Each column center uses observed finite values only. A missing entry is replaced by that center, so it is zero after centering. A column is active when at least two observed values have a population deviation above the preparation tolerance. Rows are ordered by recorded time and then state key. The fit centers the active columns and diagonalizes their Gram matrix with a deterministic Jacobi rotation. A Gram eigenvalue divided by the row count `n` is the population variance, the same divisor used for preparation. The default request is two components, and the retained count also stops at the centered rank and at eigenvalues above `1e-8` of the active total. Each component is signed so its largest-magnitude loading is positive, with the lowest flat index breaking a tie. Loadings are variance contributors, not causes. Transforming a later vector reuses the fitted centers and loadings. It requires the same `LatentSourceContract` the fit recorded: feature semantics and order, scaling, fitted center and scale, nonvarying status, observed counts, source block factors, effective block counts, multiscale segment order and factors, and the protocol identifiers. The same column names with different centers or scales are `INCOMPATIBLE_PREPARATION`. A different width, order, semantic, or factor is `INCOMPATIBLE_LAYOUT`. The transform does not refit.

`projectStateMap` runs that path once for one check-in dataset and the wearable list captured with it: the alternating graph, contextual evidence, base encoding, local preparation, local context, fixed multiscale projection, and one retrospective PCA. It writes nothing to Room and does not attach coordinates to `CausalMultiscaleInput`. The Jacobi fit grows with the number of states and is for the current prototype history. States are not dropped or sampled. The projection stays retrospective and dataset-relative. It is not a prediction and not a recommendation. Component orientation has no fixed meaning, so the map is not a primary Insight. The production Insights screen shows only the stored-history baseline and does not subscribe to this fit or to behavior associations. A debug build can open Research preview from Profile. That route is absent from a release build. The state-map pane is the subscriber for this fit, and only while that pane is composed. Choosing a point there reuses the fitted result. Edges follow resolved state-to-state links in the stored direction. A wake or day-start interval is not an edge, and a later start is not swapped into order. A state whose outgoing local context is not yet available is outlined and, when selected, says context is still accumulating.

`projectBehavioralEvidence` organizes the same graph and contextual evidence into behavior identities and interval frames. It does not estimate an effect, rank a behavior, write an insight, fit another latent model, or write Room. An identity is an activity option, a workout option, a food item, a meal-size label, or a usage option plus intent. It uses the stored option id, or the encoder's trimmed, whitespace-collapsed, root-locale name key when no option id exists. The displayed name stays beside that key. The same text in two categories is two identities. Supportive and coping usage are two identities. An amount unit does not split usage presence. A reviewed `none` is known absence for that category. A reviewed `entries` list is what was present. Unreviewed, absent, and conflicting stay unknown and are not turned into absence. The projection does not expand a row for every catalog option that was not listed. The catalog is every identity reported in the history it was given, so a later leakage-safe evaluation has to fit the catalog on training history only. A wake or day-start interval can carry the ending state and cannot carry an invented start, a starting emotion, or a measured delta. A resolved starting state carries its explicitly recorded emotion. An empty emotion stays missing rather than becoming a token. The ending emotion is the ending check-in's recorded emotion, when one was stored. A delta exists only when that axis was explicit at both ends of a real earlier-to-later link. Calendar days use `TemporalWindowProjector`: local midnight to the next local midnight in the supplied zone. A completed interval contributes exposures to a day only when the whole stored interval is contained. An interval that crosses midnight stays whole and is overlapping, not attributed. An incomplete interval can appear in that day's coverage and is not a completed exposure. Identical check-ins stay separate occurrence ids. None of these frames are written onto `CausalMultiscaleInput`.

`projectBehaviorAssociations` reads that evidence dataset and builds one descriptive profile per catalogued behavior. The protocol is `behavior-association-v2`. `behavior-association-v1` is the earlier result shape without emotion distributions. The identifier names the result contract, so the added fields take a new version. The result stays pre-release and internal: it is not stored, and Insights does not show it. It is retrospective, within this history, and dataset-relative. It is not causal, not predictive, and not sufficient for a recommendation. It does not read PCA coordinates, rank behaviors, compute a p-value, or write Room. Mood, Energy, Confidence, and Anxiety stay separate raw values. Anxiety is not inverted. An interval is present when its category was reviewed and the identity was listed, absent when that category was reviewed and the identity was not listed, and unknown when the category is unreviewed, missing, or conflicting. Unknown is never stored as absence. An incomplete interval, a reversed window, or invalid chronology is excluded from every lens. A boundary interval may still contribute an ending value. It does not contribute a start or a delta. A delta is ending minus starting, and only for an axis recorded at both ends. Each numeric summary reports a count, mean, population deviation, minimum, and maximum. No observations leave the summary unavailable. Contrasts are present mean minus absent mean, and both support counts stay beside the difference. Calendar-day association first averages the explicit readings inside one day, then summarizes those day means, so a day with several check-ins has the same weight as a day with one. A day is present when a fully contained completed interval reports the behavior. It is absent only when every contained completed interval was reviewed, none reported the behavior, and no incomplete or overlapping interval makes that absence ambiguous. Workout minutes and usage amounts stay beside presence. Units are not combined, and quantity is not correlated with an axis in this pass. Each profile also keeps four categorical emotion distributions: present and absent starting emotions, and present and absent ending emotions. Each distribution counts eligible observations, how many recorded an emotion, how many did not, and the token counts in stored-name order. Labels are not numbered, averaged, combined, or ranked.

`observeBehaviorAssociations` is the debug subscriber for those profiles. It reads one check-in snapshot at a time, builds the alternating graph once, and projects behavioral evidence from that graph. The same evidence feeds associations, context balance, and exposure episodes. It does not build the evidence a second time. Equal snapshots are not projected again. A newer snapshot cancels an older projection. Selecting a behavior or expanding a detail, including context balance or exposure episodes, does not project again. The on-device inspector uses the device zone, and tests inject the zone. The association pane and the state-map pane share the debug research route and subscribe only while that pane is composed. Neither view model is used by Insights. The inspector is an audit surface: it shows support, means, differences, emotion counts, calendar-day association, quantity coverage, context balance, and exposure episodes. It does not color a difference, call it an effect, rank behaviors, or write Room.

`projectBehaviorContextBalance` reads that evidence dataset and the association classifications. The protocol is `behavior-context-balance-v1`. It is retrospective, descriptive, within this history, and dataset-relative. It is not causal, not predictive, not an adjusted behavior difference, and not sufficient for a recommendation. It rejects inputs whose catalog scope, behavior identities, interval keys, or calendar zone disagree, rather than joining partial histories. It does not reclassify intervals. Unknown and excluded intervals stay out of the present and absent summaries. Each interval receives a context descriptor: stored instants, duration, local clock minutes, cyclic sine and cosine, starting core axes with explicit missingness, and time since waking when a stored wake anchor is unambiguous. Clock time is cyclic, so 11:30 PM and 12:30 AM are one hour apart. The interval midpoint describes the stored window and is not an inferred event time. A reversed window has no midpoint. A wake anchor is the stored start of a completed, well-ordered `wake_time` boundary. A day-start boundary is not a wake anchor. An anchor applies only on its own local date, and only when the latest applicable anchor is unique. An interval whose endpoints select different anchors leaves time since waking unavailable. Yesterday's wake is not carried across midnight. Present and absent groups keep separate circular summaries for start, end, and midpoint, plus population summaries of duration, time since waking, and each starting core axis. Anxiety is not inverted. Missing axes stay missing. Every present interval is paired with every absent interval for audit. A pair uses start-clock, end-clock, and midpoint gaps, duration gap and ratio, start time-since-wake gap, and the root-mean-square of raw 0–10 starting axes recorded on both sides. Ending axes, deltas, ending emotions, and association contrasts are not pair inputs. Nearest opposite intervals are summarized separately for end clock, midpoint clock, starting-axis distance, time since waking, and duration. Those distances are not combined into one weight. The debug profile can show the summaries. It does not show the pair list, and it does not label a behavior balanced, confounded, or adjusted.

`projectBehaviorExposureEpisodes` reads that evidence, the same alternating graph, and the association classifications. The protocol is `behavior-exposure-episode-v1`. It is retrospective, descriptive, within this history, and dataset-relative. It is not causal, not predictive, and not sufficient for a recommendation. It does not change association or context-balance results, estimate a quantity association, or write Room. A behavior is present only when the association already says so. Unknown, unreviewed, conflicting, incomplete, reversed, and invalid intervals stay out of the episode and keep an explicit break reason. Unknown is not rewritten as absence. Two present intervals connect when the earlier interval's ending state is the later interval's resolved starting state. A wake or day-start interval may begin an episode and does not receive an invented start, even if a previous id was stored on the analysis object. Each transition ends at its own check-in, so the stored graph does not join two intervals into one state. A state may have several outgoing intervals. Those branches remain one episode. Predecessor totals follow the single earlier path and do not add a sibling. The episode-wide reported-window sum counts each member interval once and is not a continuous behavior duration. A past-only history at the start of a transition contains only that predecessor path. It does not contain the current interval, its ending state, its delta, or a later branch. A behavior with no reviewed absent interval is marked presence-contrast unavailable. Its episodes are still retained. Usage totals stay separated by normalized unit. A blank or malformed amount remains presence and makes the affected cumulative quantity unavailable. A parsed zero stays zero. A unitless cumulative rate exists only when every contributing unitless amount was parsed and the reported-window duration is positive. The debug profile can list episode structure, trajectory, co-exposures, and quantities. It does not assign a trajectory to one co-exposure.

The interval id is the ending check-in id, which is already the context window's key. The projector does not copy states, intervals, or their activity, workout, meal, or usage rows, and it does not write Room. A state is inside a window when its timestamp is in `[start, end)`. An interval whose stored `[windowStartAt, windowEndAt)` sits entirely in that range is contained. An interval that intersects the window but crosses a boundary is overlapping, and its context stays on that one interval instead of being split. An interval with no intersection is omitted. A range that covers a window and continues outside it is overlapping, not contained. A calendar day is local midnight through the next local midnight in a caller-supplied `ZoneId`, so a daylight-saving change makes that day 23 or 25 hours. That is a calendar day, not a waking day. Wake-to-wake days are not implemented. Check-ins do not store the timezone they were recorded in, so Insights uses the device zone at read time. Rolling windows use the same definition and the same projector; only the instants and the boundary basis change. `adjacentWindows` links windows that meet with no gap and no overlap, in time order. That link is temporal adjacency only. It does not associate exposures in one window with states in the next, and Insights does not offer rolling-window controls.

`projectWearables` uses those same window rules for wearable observation ids. A point belongs to the window that contains its measurement time, not its import time. A measured interval or cumulative window is contained or boundary-overlapping as a whole. Wearable values are not copied into the window and are not written onto `StateObservationV2`.

Disagreeing rows are not collapsed. `AnalysisIssue` records duplicate axis values, duplicate windows and category rows, a previous id that does not resolve, a previous check-in that is not earlier, a window end that differs from the check-in's `recordedAt`, a missing category row, a check-in with no window, a child row without its parent, a category status that disagrees with its item rows, and a completed interval that still has an `unreviewed` category. When duplicate values for one axis disagree, that axis is left out of the value map and listed on the state as conflicting, so it is not counted as ordinary missingness. When they agree, the recorded value is kept and the duplicate is still an issue. `CheckInAxisValue` and `CheckInContextWindow` already reject a value outside 0–10 and a start later than its end, so those two malformed shapes cannot enter this builder.

`summarizeCheckInAnalysis` counts states, completed and incomplete intervals, linked transitions, measured-delta transitions, wake and day-start intervals, missingness per core axis, `none` versus `entries` per category, and issues. Those counts describe the projection. They are not effects or causes.

## State representation

The ten-axis encoder below is unused at runtime. Nothing in `OrbitApplication`, sync, or the Health screen calls it. The description is kept so a later deletion pass can see what the dormant files do.

`domain/state/StateEncoder.kt` can read Room observations and the latest biometric snapshot, then persist a `StateVectorSnapshot`. `FeatureAxes` fixes the following ten dimensions.

| Axis | Current encoding |
| --- | --- |
| Current mood | Last committed mood score divided by 10 |
| One-hour mood change | Current mood minus the earliest sample in the preceding hour, mapped from −10…10 to 0…1 |
| Latest sleep hours | Latest manual sleep duration, otherwise biometric sleep; divided by 12 |
| Resting heart rate | Latest biometric value mapped using 40–100 BPM |
| Steps today | Latest biometric step count divided by 15,000 |
| Activity load | Duration from selected activity events in the preceding 24 hours, divided by 180 minutes |
| Workout load | Duration from selected workout events in the preceding 24 hours, divided by 120 minutes |
| Supportive-use count | Number of events with SUPPORTIVE intent in the preceding 24 hours, divided by 4 |
| Coping-use count | Number of events with COPING intent in the preceding 24 hours, divided by 4 |
| Meal regularity | Heuristic derived from meal count in the preceding 24 hours; not a measure of meal timing |

Values are clamped to 0–1. Missing sources generally use 0.5 with the corresponding presence bit unset. The mood and mood-change axes currently always set their presence bits, including when mood is still the default or the one-hour sample window is empty. This needs a separate missingness decision.

Food identities, nutrient composition, specific activity categories, medication identities/doses, and arbitrary event order are not axes in this representation. They should not be described as inputs to the present clustering model. One-hour change and 24-hour aggregates provide limited temporal context, not sequence modeling.

## Encoding and analysis orchestration

`BiometricRepository.sync()` reads Health Connect and upserts `WearableObservation` rows. It does not encode a state vector, ingest topology, or write `BiometricSnapshot`. `BiometricSyncWorker` is a daily fallback. Startup cancels the old hourly unique work named `hourly_biometric_sync` and enqueues `daily_wearable_sync`. Android still chooses the exact run time. Startup also cancels any previously enqueued `TopologyCompactWorker`. If a leftover compaction job runs, its `doWork` returns without writing.

Saving a completed check-in schedules one separate one-time interval import, `wearable_interval_capture:<checkInId>`, with `ExistingWorkPolicy.KEEP`. The schedule runs after the completion transaction returns, so the save and navigation do not wait on Health Connect. A scheduler failure leaves the check-in saved. Discard does not schedule an import. The worker loads the stored `CheckInContextWindow` and uses its `windowStartAt`, `windowEndAt`, and `startBasis`. It does not resolve the boundary again. A missing or unfinished window returns without a read. The worker distinguishes a captured observation, a valid empty read, Health Connect being unavailable or unpermitted, and a failed read. A capture returns success. An empty or failed read returns `Result.retry()` on that same unique request while fewer than two retries have occurred, with a 15-minute linear backoff, then success. Unavailable or missing permission finishes without a retry. Each attempt reads the stored window again. After the request succeeds, `KEEP` does not start another one.

The interval import asks Health Connect to aggregate steps and heart rate over `TimeRangeFilter.between` of those stored instants. It also keeps the latest resting-heart-rate record whose time falls inside the interval, without using that point in place of the average. The stored observation uses the same instants. A true zero is stored. Individual step records are not summed in place of a missing aggregate. Resting-heart-rate and heart-rate samples are kept only when their measurement time is inside `[windowStartAt, windowEndAt)`. Sleep is not invented for the waking interval. Sleep sessions remain their own observations. A later manual sleep log does not rewrite the context window. The daily fallback still imports the selected day summary: steps from the anchor instant’s local midnight through that instant, the latest resting heart rate in seven days or else a six-hour average or latest sample, and the latest sleep session in 48 hours. The midnight comes from `anchor.atZone(zone).toLocalDate()`, not from `LocalDate.now`.

A sync imports selected summaries, not an exhaustive sensor stream. Raw record reads continue through `pageToken` until it is null or empty. Health Connect deletions are not reconciled. The Health screen is connection and status only: availability, permission, a manual import, the latest import time, which metric types are stored, and sync notes. It does not list raw observations. Insights reads the stored observations only to tell whether any have been recorded.

A wearable observation keeps its metric, value, unit, measurement start and end, temporal kind, measurement or aggregation method, Health Connect as the import source, the originating app package when a record provides it, the Health Connect record id when one exists, the recording method when a record provides it, and the import time. A missing permission or an unavailable metric is the absence of a row. A genuine numeric zero is stored. A heart-rate average and an individual heart-rate sample are not stored as resting heart rate. Steps from an aggregate call are one cumulative window. Overlapping cumulative windows are separate rows and are not added together. A confirmed `SleepEvent` and a wearable sleep observation stay in different tables.

Identity depends on what Health Connect actually provides. A record-backed observation uses source, metric, method, and the stable record id, so a corrected value or measurement time replaces that row. A blank record id is absent and the row is identified by its measurement window instead. A heart-rate sample has no sample id. Its key is the parent record id plus the sample timestamp, so samples from one parent stay distinct and reimporting the same sample replaces it. An aggregate has no record id. Its key is source, metric, method, and the exact requested start and end, so a later sync instant is a different steps or average row. Sleep stages are not copied. The session start, end, and duration are. Records also carry a zone offset; the stored times are the absolute instants.

`WearableObservationRepository.observe()` is the full local history used by later analysis. Coverage counts are derived in memory and are not written back. Insights uses only whether any observation exists. The Health screen keeps the metric counts, measurement span, and latest import time. Neither surface correlates wearables with check-ins or makes a recommendation. A check-in row in History lists wearable observations contained in that stored interval: the exact steps or heart-rate aggregate from the interval capture when one exists, and the latest resting-heart-rate point whose measurement time falls inside it. A wider aggregate, such as midnight through a later sync, overlaps that interval and is left off the row. Those values stay on the wearable observation. They are not written onto the check-in. Sleep is not listed on that row yet. The stored observations and the context window’s start and end are the inputs that projection will use.

## Neighbors and grouping

`FeatureDistance.rms()` computes root-mean-square distance over shared observed axes. Different pairs can be compared on different subsets, so missingness affects both interpretation and neighbor-search behavior.

`HnswIndex` is a custom, two-layer approximate graph index (`MAX_LEVEL = 1`). Parameters include construction search width 32 and base-layer neighbor cap 16. Eviction uses tombstones; compaction rebuilds the working graph.

`TopologyRepository` uses five non-self neighbors to estimate core distance (`MIN_PTS = 6` including the point), and uses a threshold derived from the 90th percentile of finite core distances during compaction. It groups core points using mutual reachability and connected components. This is a custom approximation, not an implementation of hierarchical cluster stability selection.

## Candidate suggestions

`NeighborhoodSuggester` first searches sufficiently large groups for a target with higher mood, then falls back to up to three higher-mood neighbors. It returns feature deltas, or a learning message when appropriate. Mood and mood-change axes are excluded from the returned deltas.

`suggestBetterNeighborhood()` is not called from application startup, sync, or the Health screen. The synthetic harness remains source code and is covered by unit tests. It is not constructed, and its outputs are not shown. No causal or clinical efficacy claim follows from those tests.

## Storage and communication

Room schema version 23 contains the observation and legacy analysis tables, including configurable check-ins, their context windows, contextual activity, workout, usage, and meal items, and `wearable_observations`. Schema 22 added `emotion` to `check_ins` with an empty default for rows already stored. Schema 23 adds the wearable table and does not rewrite check-ins. The check-in analysis projection is still `check-in-analysis-v2`, sourced from Room schema 22's check-in entities, and derived in memory by `CheckInAnalysisRepository`. Wearable coverage is a separate in-memory view. Neither view is written back to Room. SQLCipher encrypts that database, and Tink / Android Keystore protect its passphrase. The last committed mood is also stored in app-private SharedPreferences; not all state is covered by the database encryption claim.

Open Food Facts requests and configured SMS shares are explicit external communication paths. Inbound SMS handling currently ignores triggers. This source does not include a hosted account or synchronization service.
